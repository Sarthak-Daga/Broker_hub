## 1. Core Concept

Unlike flats, plots are independent properties.

They must NOT belong to the existing hierarchy:

Area → Colony → Wing → Floor → Flat

A plot should be independently registered and managed.

However, it should reuse existing relationships such as Area, Seller, Client/Buyer, and Employee wherever appropriate.

## 2. Plot Information

Each plot should contain:

**Basic details**
- Unique ID.
- Property title/reference (optional).
- Area.
- Location/address.
- Remarks/description (optional).

**Dimensions**
- Length.
- Width.
- Measurement unit (initially feet).
- Total area in square feet.

Calculate automatically:

Total Area = Length × Width

Example:
- Length: 100 ft
- Width: 30 ft
- Total area: 3,000 sq. ft.

Dimensions must be positive numbers.

**Pricing**
- Asking price per square foot.
- Total asking price.

Calculate automatically:

Total Price = Total Area × Price Per Sq. Ft.

Example:
- Area: 3,000 sq. ft.
- Price: ₹5,000/sq. ft.
- Total: ₹1,50,00,000.

Use appropriate database numeric types for financial values. Do not rely on floating-point precision for monetary calculations.

## 3. Seller Relationship

A plot should be associated with an existing Seller record wherever possible.

Requirements:
- Select an existing seller when adding a plot.
- Display seller details on the plot.
- View plots associated with a seller.
- Allow an unassigned seller if the existing workflow supports it.

Do not create another Seller model.

Inspect the current Seller schema before deciding the relationship.

## 4. Plot Status

Use three statuses:

- AVAILABLE
- UNAVAILABLE
- SOLD

**AVAILABLE**
- Plot is available for purchase.
- It can be considered for buyer matching.

**UNAVAILABLE**
- Temporarily unavailable.
- Should not appear as an available property.

**SOLD**
- Plot has been sold.
- Sale details must be recorded.

Use the existing project's enum conventions.

## 5. Sale Tracking

When a plot is marked SOLD, the user must select:

- **Sold To:** The buyer/client who purchased the plot.
- **Sold By:** The employee who handled the sale.

Both should be selected from existing database records.

Requirements:
- Buyer/client is mandatory when marking SOLD.
- Employee is mandatory when marking SOLD.
- Validate both on the server.
- Save the relationships along with the status update.
- Display buyer and employee names on sold plot cards.

When changing a sold plot back to AVAILABLE or UNAVAILABLE, clear the current sale associations unless an existing sale-history mechanism is available.

Inspect the existing Flat sale-tracking implementation and follow its conventions.

Do not blindly copy flat-specific relationships.

## 11. Strict Prisma 8 RC Rules

This project uses Prisma 8 RC and a contract-based schema.

Our database access pattern uses:

`import { db } from "@/prisma/db";`

Examples:

`db.orm.public.Model.all()`

`db.orm.public.Model.create(...)`

`db.orm.public.Model.where({ id }).update(...)`

`db.orm.public.Model.where({ id }).delete()`

Do not switch to traditional Prisma syntax such as:

`prisma.model.findMany()`

Do not blindly suggest classic `npx prisma migrate dev`.

Follow the existing contract and custom migration workflow.
